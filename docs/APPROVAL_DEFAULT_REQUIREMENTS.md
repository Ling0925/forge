# Forge 审批提示默认值改为 Y/n 需求

本文是**命令行审批提示默认值**的需求文档：把 `[y/N]`（默认拒绝）改为 `[Y/n]`（默认批准）。
它描述目标行为、现行实现、改动点、安全影响与验收标准，**不是**已通过验收的声明。

- 相关契约：[CLI.md](CLI.md)（终端审批）、[ARCHITECTURE.md](ARCHITECTURE.md)、[APPROVAL_MODE_REQUIREMENTS.md](APPROVAL_MODE_REQUIREMENTS.md)（审核模式总需求）。
- 术语：**默认值**指用户在提示符处**直接回车**（空输入）时系统采取的动作。

## 0 前置声明（必读）

> **本需求把审批默认从"拒绝"反转为"批准"，与 `docs/CLI.md` 现记载的"审批默认拒绝"直接冲突。**

相关既有约定：

- `docs/CLI.md:50`：**"审批默认拒绝。……仅用请求出现之后新输入的 `y` 加 Enter 授权。"**
- 现有 4 处提示文案均为 `[y/N]`（小写 y = 默认否）。
- 解析逻辑**仅** `y`/`yes` 视为批准，空输入即拒绝（见 §2）。

因此落地时**必须同步更新** `docs/CLI.md`，否则文档与代码矛盾。本需求由需求方**明确指示**（"我需要 Y/n"），风险由需求方承担；实现方仍需保留 §5 的安全约束。

## 1 需求摘要

1. 命令行审批提示文案由 `Approve? [y/N]` 改为 **`Approve? [Y/n]`**。
2. 用户**直接回车（空输入）**即视为**批准**。
3. 输入 `n`/`no` 仍明确拒绝；输入 `y`/`yes` 仍明确批准。
4. 粘贴、预输入、历史回忆等**非本次新输入的授权路径不得放宽**（见 §5）。

## 2 现状（经代码核对）

提示文案（4 处，均为 `[y/N]`）：

| 位置 | 代码 |
| --- | --- |
| `src/cli/terminal/controller.ts:253` | `this.approval("Approve? [y/N] ", signal)` |
| `src/cli/format.ts:245` | `span("Approve? [y/N]", "warning")` |
| `src/cli/cli.ts:680` | 提示串结尾 `Approve? [y/N] ` |
| `src/cli/interactive.ts:612` | 提示串结尾 `Approve? [y/N] ` |

解析逻辑（3 处，空输入均判为**拒绝**）：

| 位置 | 代码 | 语义 |
| --- | --- | --- |
| `src/cli/terminal.ts:271-281` | `["y","yes"].includes(answer.trim().toLowerCase())` | 空 → 不在集合 → **false** |
| `src/cli/cli.ts:685` | `/^(y\|yes)$/i.test(answer.trim())` | 空 → 不匹配 → **false** |
| `src/cli/interactive.ts:620` | `/^(y\|yes)$/i.test(answer.trim())` | 空 → 不匹配 → **false** |

相关安全机制（**必须保留**）：

- **fresh 语义**：审批用 `question(prompt, signal, { fresh: true })`，开会话时**清空排队输入**（`terminal.ts:229-232`）。
- **粘贴不构成授权**：`tests/cli/run-input.test.ts:103-118` 断言"排队/粘贴的 `y` 不能批准一个新鲜审批"。
- **中止即拒绝**：`readApproval` 的 catch 返回 `false`（`terminal.ts:278-280`）；`signal.aborted` 检查在批准前。

## 3 目标

1. 空回车 = 批准；`n`/`no` = 拒绝；`y`/`yes` = 批准。
2. 文案与行为一致：显示 `[Y/n]` 时默认确实是批准。
3. 不削弱既有的"粘贴/排队不算授权"防线。

## 4 非目标

- 不改变**何时**请求审批（那属于审核模式，见 `APPROVAL_MODE_REQUIREMENTS.md`）。
- 不改变**非交互**路径：非 TTY 仍拒绝（`cli.ts:673-678`），`--yes` 仍仅限 `unrestricted`（`cli.ts:672`）。
- 不改变桌面审批面板（它是按钮，非 `y/N` 文本；见 §6）。
- 不改变 `mode=plan` / `permission=readonly` 的强制只读语义。

## 5 安全与边界约束（强制）

- **R-X1**：**只有"本次、新输入的、显式的空回车"**才算默认批准。
  - **不得**让排队输入（queue）中的空行触发批准。
  - **不得**让粘贴内容（bracketed paste）中的空行/换行触发批准。
  - 实现必须沿用 `fresh` + `tainted` 机制：若输入行来自粘贴或非新输入，**不得**因"为空"而批准。
- **R-X2**：中止（abort）、EOF、异常路径**仍判为拒绝**，不得因默认批准而误放行。
- **R-X3**：非 TTY 与非交互路径**不适用**本默认值，行为不变。
- **R-X4**：`plan`/`readonly` 下不产生写操作审批放行。
- **R-X5**：文档（`CLI.md`）必须同步更新为"默认批准"，并**明确风险提示**：命令不是沙箱。
- **R-X6**：文案变更必须让"默认"一眼可辨（大写 `Y`），并在首次进入该模式时给出风险告知。

### 5.1 需要重点设计的一处风险

**空回车批准**与"防误触"存在张力：用户误按回车就会批准一次高危命令。建议至少满足其一（见 §7 Q2）：

- 风险提示：审批卡片明确写出"回车=批准"；
- 或对**高危工具**（如 `run_command`）保留"必须显式输入 y"，
  仅对低危工具采用空回车批准。

## 6 桌面端一致性（范围）

桌面端 `ApprovalPanel` **没有** `y/N` 文本，是"允许本次/拒绝"两个按钮，且"允许本次"已是 `primary` 主按钮（视觉默认偏批准）。因此：

- 本需求的**必改范围是 CLI 的 4 处文案 + 3 处解析**。
- 桌面端**是否需同步**（例如把"回车=允许"绑定）需明确，见 §7 Q3。

## 7 待决问题

- **Q1**：`no` / `n` 之外，其他非空输入（如 `maybe`）应视为拒绝吗？（现在是非 y 即拒绝，建议保持）
- **Q2**：是否对所有工具采用空回车批准，还是仅低危工具？高危是否要求显式 `y`？
- **Q3**：桌面端是否需要同步"回车=允许"？
- **Q4**：`CLI.md` 的"审批默认拒绝"改写的措辞与风险提示文案？
- **Q5**：是否有一次性"本次会话默认批准"的开关，与逐次回车区分？

## 8 验收标准

- **AC-1**：提示文案为 `Approve? [Y/n]`（4 处一致）。
- **AC-2**：空回车 → 批准；`y`/`yes` → 批准；`n`/`no` → 拒绝；其他 → 拒绝。
- **AC-3**：**粘贴的空行/换行不批准**；**排队的空行不批准**（不回归 `run-input.test.ts` 的既有断言）。
- **AC-4**：中止/EOF 仍拒绝。
- **AC-5**：非 TTY、非交互路径行为不变。
- **AC-6**：测试更新：
  - `tests/cli/format.test.ts:141`、`render-v2.test.ts:394,439`、`composer.test.ts:93`、`scroll-selection.test.ts:149,152` 的 `[y/N]` 断言更新为 `[Y/n]`；
  - 新增"空回车批准"与"粘贴/排队空行不批准"的用例。
- **AC-7**：`docs/CLI.md` 同步更新。
- **AC-8**：`pnpm typecheck` 与 `pnpm test` 通过；CLI 改动按仓库约定 `node scripts/build-core.mjs` 后重开 `forge` 生效。

## 9 风险与约束

- **最高风险：误触批准**。空回车是极低成本的输入，会显著抬高"意外执行高危命令"的概率。必须在 §5.1 做取舍。
- **文档冲突**：不改 `CLI.md` 会造成文档与代码矛盾。
- **测试面**：至少 8 处既有断言引用 `[y/N]`，需同步更新（列于 AC-6）。
- **与审核模式需求叠加**：若同时落地 `APPROVAL_MODE_REQUIREMENTS.md` 的 `full access` 默认，则"默认批准"会出现两次，需统一为单一默认来源，避免双重放宽。
- **并发工作**：工作区存在其他任务的在途改动，实现时不得覆盖。
- **本机流程**：按 AGENTS.md，本机 CLI 更新走"改代码 → `node scripts/build-core.mjs` → 重开 `forge`"，不做完整发布/打包。

## 11 实施状态（2026-10-14）

阻塞：与 APPROVAL_MODE_REQUIREMENTS R-S4/AC-5 的 manual 默认拒绝矛盾，需明确最终默认策略与高危工具范围。本轮未改 `[y/N]`、fresh/tainted、abort/EOF/non-TTY 和只读边界。不可仅改提示/正则：现有 tainted、Escape 等路径以空串表示拒绝，直接让空串批准会造成授权漏洞，落地前须分离拒绝与新鲜空回车。

## 最终决策与实施（2026-10-14，取代上文冲突/阻塞描述）

需求方已直接确认：默认 full access；切到 manual 后空回车默认确认。此决策覆盖此前 manual 默认拒绝的要求和未决 Q0。实现于交互 CLI：full-access 自动回答所有权限内审批（含 MCP/浏览器/子代理），auto 保留根会话命令范围；manual/ask 为逐次 [Y/n]。模式只在本 CLI 进程保留，/new、/resume 保持用户选择，重启默认 full-access。桌面仍为原按钮交互，非交互 run/resume 的 --yes/unrestricted 约束不变。

安全实现：Esc/Ctrl+C/粘贴或历史污染/Shift+Enter 以明确 no 拒绝，不再用空串表达拒绝；fresh 清队列、独立编辑器与 paste provenance 保留；await 后再次检查 abort/关闭；其他非空输入（包括纯空白）拒绝。plan/readonly 不调用批准 UI。默认及切换有非沙箱风险提示，自动请求逐项回显并每轮汇总；记录过滤常见 token/密码参数，不保证识别任意未知秘密。

本轮验证：12 个 CLI 聚焦测试文件、193 项用例通过；`tsc --noEmit`、`node scripts/build-core.mjs`、临时 FORGE_HOME 的 --help 启动检查通过。未运行全量测试、真实命令/MCP/浏览器副作用验收或桌面打包；不会因测试而使用真实密钥。
