# Provider protocols

Search uses the **Responses-native `web_search` hosted tool**, explicitly enabled with `forge config set --api-mode responses --web-search live` (`cached` disables external web access; omitted/`disabled` keeps search off). Forge requests `web_search_call.action.sources`, validates search lifecycle events and `response.output_text.annotation.added`, and persists search items and URL annotations for same-origin continuation. Separate bounded citations/search records drive CLI and renderer source lists; hosted operations never become local function calls or fabricated tool outputs. Incompatible protocols or rejected tools fail without a Bing/function-tool fallback. Search-enabled generation requests are not automatically retried because remote execution/billing may already have happened. `web_fetch` remains a separate local reader for specified public URLs. See [WEB.md](WEB.md) for request-level approval, provider data/fee boundaries and limitations.

HTTP requests and SSE decoding use the official `openai` and `@anthropic-ai/sdk` TypeScript SDKs. Forge retains message/tool mapping, gateway compatibility validation, bounded output, safe errors and runtime retry policy. `apiMode` explicitly selects `chat-completions`, `responses`, or `anthropic`. Omitted or `chat-completions` uses the existing `/chat/completions` adapter, including its existing streaming and narrowly scoped nonstream fallback. `responses` uses **POST `/responses`** with `stream: true`, `store: false`, `input`, and native flat function definitions (`type: "function"`, `name`, `description`, `parameters`, `strict: false`). Select a mode only when your gateway/model supports that protocol. There is no model fallback, mode autodetection, or automatic replay of an uncertain Responses POST.

Responses input maps system/user/assistant text to role/content items, assistant tool calls to `function_call` items, and matching tool messages to `function_call_output` items keyed by `call_id`. The adapter requires every call to have a matching output before sending the next request. It parses incremental `response.output_text.delta` and `response.function_call_arguments.delta`, validates completed output and IDs against deltas, and only accepts `response.completed` with `status: completed`. Failure, incomplete, error, missing terminal, malformed calls/arguments, unexpected output types, or trailing events reject the response. Request timeout/cancellation and byte/text/event caps also apply. Usage is mapped from `input_tokens`, `output_tokens`, `total_tokens`, and **reported** `input_tokens_details.cached_tokens` (including zero); absent cache counts remain absent. HTTP and protocol errors do not echo server bodies, keys or tool arguments.

Reasoning continuation: `include: ["reasoning.encrypted_content"]` requests opaque reasoning output items. Completed, ordered original output (up to 256 output items; the persisted `providerState` is capped at **256 KiB**, with a 250000-byte wire-output validation) is attached to the exact assistant message as versioned `providerState`, persisted with the session and copied on fork. On matching Responses endpoint and model it replays those original items once, followed by generic tool results; on a different endpoint or model it drops opaque foreign reasoning and serializes generic assistant text and completed tool calls with their paired results. Histories with unresolved or unpaired tool calls reject before the request. A single-response compatibility rule handles gateways whose `response.completed` has `status: completed` but `output: []`: only after stream completion, it uses the ordered original `output_item.done` items when every added item has exactly one matching done item at contiguous indices, unique item IDs, consistent identity, completed function arguments and message text matching tracked deltas and done events, and no conflicting response ID in created/in_progress/completed events. It preserves opaque reasoning from the done event unchanged. Missing terminal, incomplete or failed status, unfinished text/arguments, missing or duplicated items, and conflicting names or call IDs reject before exposing tool calls. Nonempty terminal output remains subject to strict full correspondence with done items; this rule does not synthesize items, retry, replay uncertain requests, or imply support for other gateway deviations. After a validated `response.completed`, the SSE transport may optionally carry exactly one standalone `data: [DONE]` marker (with no event name). It is not a substitute for `response.completed`: premature, repeated, or followed-by-data markers reject; streams without the marker remain valid. Chat Completions requests omit providerState. This metadata is internal state, not display text; redacted/non-resumable exports may omit it. The supported output item types are assistant `message` with `output_text` and URL annotations, `function_call`, opaque `reasoning`, and authorized `web_search_call`. Search supports `search`, `open_page` and `find_in_page` actions; its lifecycle/annotation events are identity-checked against completed output. Search progress is ephemeral; only validated final records are persisted. SSE accepts exact `response.created`, `response.in_progress`, `response.content_part.added/done`, `response.output_text.done`, `response.reasoning_summary_part.added/done`, and `response.reasoning_summary_text.delta/done`, as well as the validated delta/item/completion events described above. `response.reasoning_summary_text.delta` is a bounded, display-only preview forwarded to the provider observer's optional `onReasoning`; it never becomes assistant content and is not the opaque continuation. The accumulated preview (capped at 128 KiB) is also returned on the assistant message's optional `reasoning` field for persistence; Chat Completions `reasoning_content` is handled the same way. Stored `reasoning` is never sent back to the provider. Other lifecycle and multimodal events are unsupported. Native Anthropic Messages is described below; no native Gemini protocol adapter is provided.

Protocol references: https://developers.openai.com/api/docs/guides/function-calling , https://developers.openai.com/api/docs/guides/streaming-responses , and the OpenAI Responses API reference. Local HTTP fixtures verify implemented wire behavior, **not** authorized gateway interoperability; verify against your own gateway before relying on a specific deployment.

## Anthropic Messages

Select `apiMode: "anthropic"` for the native Anthropic API or a compatible Messages gateway. Use `https://api.anthropic.com` as the base URL; a trailing `/v1` is also accepted and normalized. Custom gateway path prefixes are retained. The SDK supplies `x-api-key`, the API version header and native `/v1/messages` and `/v1/models` routes. Forge supplies explicit credentials and does not inherit OpenAI/Anthropic SDK environment credentials. An empty key supports unauthenticated local gateways.

System instructions map to the top-level `system` field; user images become native base64 image blocks. Tools map to `input_schema`, complete `tool_use` blocks and paired `tool_result` blocks. The SDK assembles streaming text, thinking and tool JSON; Forge validates complete arguments and stop reasons before returning calls to the executor. Truncation, refusal, malformed tool arguments and missing terminal messages fail without executing partial tools. No server-hosted tools are exposed by this adapter.

Signed `thinking` and `redacted_thinking` blocks are stored in the existing bounded `providerState`. They replay only for the same normalized endpoint and model, after checking text and calls against the assistant message. Switching endpoint/model rebuilds text and tool history without foreign signed thinking. Display-only reasoning stays capped at 128 KiB. Usage includes input, cache creation and cache read tokens; cached prompt tokens reflect only the provider-reported cache reads.

Anthropic requires `max_tokens`: Forge defaults to 8192. Optional shared `maxOutputTokens` (`forge config set --max-output-tokens NUMBER`) overrides it; OpenAI maps the same explicit setting to `max_completion_tokens` or `max_output_tokens`. With no setting, OpenAI keeps its previous server-default behavior. Anthropic `minimal/low/medium/high/xhigh` request thinking budgets of 1024/1024/4096/8192/16384, capped below the output limit. Thinking requires an output limit above 1024. `default` omits thinking; `none` sends `disabled`. Model support varies; no automatic effort downgrade occurs.

Both SDK generation clients use `maxRetries: 0`; existing Forge runtime retry policy remains the sole generation retry owner. The SDK SSE decoder is also used for OpenAI gateway streams while retaining Forge's terminal/tool integrity checks. Its exported event-preserving decoder entry point is covered by the gateway regression fixtures and must be rechecked on SDK upgrades. The transport wrapper adds byte/UTF-8 limits and an idle timer, including partial frames and heartbeat comments; it does not implement an SSE parser.

SDK references: [OpenAI TypeScript](https://developers.openai.com/api/reference/typescript), [Anthropic TypeScript](https://platform.claude.com/docs/en/cli-sdks-libraries/sdks/typescript). Local HTTP and browser fixtures do not establish interoperability with a particular live account or gateway.
