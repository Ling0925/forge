# Provider protocols

Search uses the **Responses-native `web_search` hosted tool**, automatically available with live web access on ordinary Responses agent requests in CLI, desktop and Web. There is no search configuration switch; old stored `disabled`/`cached`/`live` values are accepted and discarded. Readonly/Plan and auxiliary requests (such as titles and compaction) still omit search, and workspace permission still requires request-level approval. Mixed-protocol routes declare search only on Responses members. Forge requests `web_search_call.action.sources`, validates search lifecycle events and `response.output_text.annotation.added`, and persists search items and URL annotations for same-origin continuation. Separate bounded citations/search records drive CLI and renderer source lists; hosted operations never become local function calls or fabricated tool outputs. Other protocols continue without this hosted tool. Rejected search tools fail without a Bing/function-tool fallback. Search-enabled generation requests are not automatically retried because remote execution/billing may already have happened. `web_fetch` remains a separate local reader for specified public URLs. See [WEB.md](WEB.md) for request-level approval, provider data/fee boundaries and limitations.

HTTP requests and SSE decoding use the official `openai` and `@anthropic-ai/sdk` TypeScript SDKs. Forge retains message/tool mapping, gateway compatibility validation, bounded output, safe errors and runtime retry policy. `apiMode` explicitly selects `chat-completions`, `responses`, `anthropic`, or native `gemini`. Omitted or `chat-completions` uses the existing `/chat/completions` adapter, including its existing streaming and narrowly scoped nonstream fallback. `responses` uses **POST `/responses`** with `stream: true`, `store: false`, `input`, and native flat function definitions (`type: "function"`, `name`, `description`, `parameters`, `strict: false`). Select a mode only when your gateway/model supports that protocol. Direct model selections have no model fallback or mode autodetection. Cross-model selection requires an explicit route group; uncertain Responses POSTs are not automatically replayed.

Responses input maps system/user/assistant text to role/content items, assistant tool calls to `function_call` items, and matching tool messages to `function_call_output` items keyed by `call_id`. The adapter requires every call to have a matching output before sending the next request. It parses incremental `response.output_text.delta` and `response.function_call_arguments.delta`, validates completed output and IDs against deltas, and only accepts `response.completed` with `status: completed`. Failure, incomplete, error, missing terminal, malformed calls/arguments, unexpected output types, or trailing events reject the response. Request timeout/cancellation and byte/text/event caps also apply. Usage is mapped from `input_tokens`, `output_tokens`, `total_tokens`, and **reported** `input_tokens_details.cached_tokens` (including zero); absent cache counts remain absent. HTTP and protocol errors do not echo server bodies, keys or tool arguments.

Reasoning continuation: `include: ["reasoning.encrypted_content"]` requests opaque reasoning output items. Completed, ordered original output (up to 256 output items; the persisted `providerState` is capped at **256 KiB**, with a 250000-byte wire-output validation) is attached to the exact assistant message as versioned `providerState`, persisted with the session and copied on fork. On matching Responses endpoint, model and authenticated credential scope it replays those original items once, followed by generic tool results; on a different endpoint or model it drops opaque foreign reasoning and serializes generic assistant text and completed tool calls with their paired results. Histories with unresolved or unpaired tool calls reject before the request. A single-response compatibility rule handles gateways whose `response.completed` has `status: completed` but `output: []`: only after stream completion, it uses the ordered original `output_item.done` items when every added item has exactly one matching done item at contiguous indices, unique item IDs, consistent identity, completed function arguments and message text matching tracked deltas and done events, and no conflicting response ID in created/in_progress/completed events. It preserves opaque reasoning from the done event unchanged. Missing terminal, incomplete or failed status, unfinished text/arguments, missing or duplicated items, and conflicting names or call IDs reject before exposing tool calls. Nonempty terminal output remains subject to strict full correspondence with done items; this rule does not synthesize items, retry, replay uncertain requests, or imply support for other gateway deviations. After a validated `response.completed`, the SSE transport may optionally carry exactly one standalone `data: [DONE]` marker (with no event name). It is not a substitute for `response.completed`: premature, repeated, or followed-by-data markers reject; streams without the marker remain valid. Chat Completions requests omit providerState. This metadata is internal state, not display text; redacted/non-resumable exports may omit it. The supported output item types are assistant `message` with `output_text` and URL annotations, `function_call`, opaque `reasoning`, and authorized `web_search_call`. Search supports `search`, `open_page` and `find_in_page` actions; its lifecycle/annotation events are identity-checked against completed output. Search progress is ephemeral; only validated final records are persisted. SSE accepts exact `response.created`, `response.in_progress`, `response.content_part.added/done`, `response.output_text.done`, `response.reasoning_summary_part.added/done`, and `response.reasoning_summary_text.delta/done`, as well as the validated delta/item/completion events described above. `response.reasoning_summary_text.delta` is a bounded, display-only preview forwarded to the provider observer's optional `onReasoning`; it never becomes assistant content and is not the opaque continuation. The accumulated preview (capped at 128 KiB) is also returned on the assistant message's optional `reasoning` field for persistence; Chat Completions `reasoning_content` is handled the same way. Stored `reasoning` is never sent back to the provider. Other lifecycle and multimodal events are unsupported. Native Anthropic Messages is described below; native Gemini is available through explicit `apiMode: "gemini"` (see below).

Protocol references: https://developers.openai.com/api/docs/guides/function-calling , https://developers.openai.com/api/docs/guides/streaming-responses , and the OpenAI Responses API reference. Local HTTP fixtures verify implemented wire behavior, **not** authorized gateway interoperability; verify against your own gateway before relying on a specific deployment.

## Anthropic Messages

Select `apiMode: "anthropic"` for the native Anthropic API or a compatible Messages gateway. Use `https://api.anthropic.com` as the base URL; a trailing `/v1` is also accepted and normalized. Custom gateway path prefixes are retained. The SDK supplies `x-api-key`, the API version header and native `/v1/messages` and `/v1/models` routes. Forge supplies explicit credentials and does not inherit OpenAI/Anthropic SDK environment credentials. An empty key supports unauthenticated local gateways.

System instructions map to the top-level `system` field; user images become native base64 image blocks. Tools map to `input_schema`, complete `tool_use` blocks and paired `tool_result` blocks. The SDK assembles streaming text, thinking and tool JSON; Forge validates complete arguments and stop reasons before returning calls to the executor. Truncation, refusal, malformed tool arguments and missing terminal messages fail without executing partial tools. No server-hosted tools are exposed by this adapter.

Signed `thinking` and `redacted_thinking` blocks are stored in the existing bounded `providerState`. They replay only for the same normalized endpoint and model, after checking text and calls against the assistant message. Switching endpoint/model rebuilds text and tool history without foreign signed thinking. Display-only reasoning stays capped at 128 KiB. Usage includes input, cache creation and cache read tokens; cached prompt tokens reflect only the provider-reported cache reads.

Anthropic requires `max_tokens`: Forge defaults to 8192. Optional shared `maxOutputTokens` (`forge config set --max-output-tokens NUMBER`) overrides it; OpenAI maps the same explicit setting to `max_completion_tokens` or `max_output_tokens`. With no setting, OpenAI keeps its previous server-default behavior. Anthropic `minimal/low/medium/high/xhigh` request thinking budgets of 1024/1024/4096/8192/16384, capped below the output limit. Thinking requires an output limit above 1024. `default` omits thinking; `none` sends `disabled`. Model support varies; no automatic effort downgrade occurs.

Both SDK generation clients use `maxRetries: 0`; existing Forge runtime retry policy remains the sole generation retry owner. The SDK SSE decoder is also used for OpenAI gateway streams while retaining Forge's terminal/tool integrity checks. Its exported event-preserving decoder entry point is covered by the gateway regression fixtures and must be rechecked on SDK upgrades. The transport wrapper adds byte/UTF-8 limits and an idle timer, including partial frames and heartbeat comments; it does not implement an SSE parser.

SDK references: [OpenAI TypeScript](https://developers.openai.com/api/reference/typescript), [Anthropic TypeScript](https://platform.claude.com/docs/en/cli-sdks-libraries/sdks/typescript). Local HTTP and browser fixtures do not establish interoperability with a particular live account or gateway.

## Persistent model catalogs

Harness-created providers share a private `$FORGE_HOME/model-catalogs/` disk cache. Successful catalog requests persist normalized model IDs, reported context-window tokens (or `null`), and fetch timestamps, not raw gateway responses or inferred windows. A hashed identity includes the source ID, endpoint, protocol and credential so sources/accounts cannot reuse each other's catalog. Files use the existing bounded atomic private-store I/O. Normal discovery and runtime window lookup read disk before networking, including after restart; there is no automatic expiry. Concurrent misses within one harness share a request, with independent reader cancellation. Failed or cancelled refreshes leave the last successful snapshot intact; cache persistence failures do not discard a usable network result.

`forge models --refresh [--source ID]` and the renderer's refresh buttons explicitly replace the catalog, including removed models and missing metadata. This is a discovery cache, not a claim of live model availability, quota or capabilities. Desktop/Web source model pickers cache complete public metadata by source, endpoint, protocol and source revision. Saving a source invalidates its previous presentation cache automatically; explicit refresh still replaces upstream discovery data. Older hosts/legacy settings without source catalogs fall back to ID lists. OpenAI-compatible (Chat Completions and Responses) and Anthropic catalogs use the same persisted metadata schema; generation requests, usage accounting and manual context-window overrides are unchanged.

## Native Gemini

Select `gemini` for `generateContent` / `streamGenerateContent`, with the Developer API base `https://generativelanguage.googleapis.com/v1beta`. Discovery follows `nextPageToken`. Native requests map inline images, tool declarations, complete function calls/results and thinking configuration; signed thought state is retained only for the same authenticated identity. Partial tools, unsupported hosted search, invalid/truncated responses and cancellation reject without fallback. Local HTTP fixtures cover streaming and nonstream responses, not live account eligibility.

## Sources, credentials, accounts and routes

`forge providers --help` and `forge routes --help` expose the same host service used by the workbench. Presets populate editable endpoints; manual/custom sources and existing `config` / `models` remain supported. Discovery selection is explicit `all`, `selected` or `none`. Model aliases never change stored upstream IDs. Private header values, proxy credentials, additional bodies and tokens are omitted from settings projections.

### Configured model choices

The conversation model picker offers only IDs explicitly saved in connection settings: the source's default model, manually added models, selected IDs, and models with nonempty parameter overrides. An upstream discovery result alone never adds a choice. `selected` still restricts choices to its saved `models`; `none` hides all choices, including the default. Legacy/environment-only settings offer their explicitly configured default model. A historical/custom current model is not silently inserted into the options or switched to another model; if no longer enabled, the composer shows a configuration warning. This is picker filtering, not a new backend authorization rule for explicit CLI/API model IDs or route members.

The settings page continues to discover the full catalog (`modelAccess({ type: "catalog", sourceId, includeUnselected: true })`) so unselected models can be added. Adding a configuration card persists a minimal manual ID even when all parameters inherit defaults; it does not freeze upstream capability metadata. Removing a non-default card removes its manual registration, selected ID and overrides. Save applies changes to the picker immediately; refresh cannot re-add an unconfigured upstream model. Restore-default clears parameter overrides, not a separately registered manual model. Source IDs isolate models with identical names.

### Per-model overrides

The Web connection page saves model settings as `source.modelSelection.overrides[modelId]`:

```ts
{
  apiMode?: "chat-completions" | "responses" | "anthropic" | "gemini";
  reasoningEffort?: "default" | "none" | "minimal" | "low" | "medium" | "high" | "xhigh" | "max";
  reasoningEfforts?: readonly string[];
  contextWindowTokens?: number | null;
  maxOutputTokens?: number | null;
}
```

- `apiMode` selects this model's request protocol. Exact selected-ID overrides win over an aliased wire model's override, then the source protocol. Omission restores inheritance; this is separate from the catalog's `protocols` capability list. Resolution selects `source.endpoints[effectiveProtocol]` or falls back to `source.baseUrl`, then selects a compatible credential. A pinned active/explicit credential that does not match fails instead of silently changing credentials or protocols. Connection authentication, headers and other private options remain source-owned. Catalog discovery continues to use the source protocol. The settings card's **请求协议** control saves this field without changing other models or the source default. This applies to API-key gateways; Vertex remains Gemini and account platforms retain their per-model adapter, rejecting incompatible explicit overrides. Protocol-specific discovery caches stay isolated; if a route has no metadata cached for its effective endpoint/protocol/credential, upstream capabilities remain unknown rather than borrowing another connection's metadata. Local model overrides still apply.
- `reasoningEffort` and a non-null `maxOutputTokens` override global request settings for that source/model. An omitted effort inherits the global setting; `default` explicitly uses the adapter's model-default behavior instead of the global effort. Null/omitted output limits inherit the global limit or existing adapter default. Upstream output-limit metadata is not automatically sent as a request limit.
- `reasoningEfforts` describes supported levels in the catalog. It does not select an effort or silently downgrade an explicit request; unknown vendor level names remain valid metadata. Empty/omitted lists restore upstream metadata.
- A non-null `contextWindowTokens` overrides catalog metadata for runtime context accounting/compaction, including models hidden by `none`/`selected`. Local windows work without a successful catalog request. Null/omitted values restore upstream metadata; the existing explicit global `modelContextWindows` override still has priority in context budgeting.
- Exact selected-ID overrides take priority per field, with fallback to the explicitly mapped wire model's overrides for aliases. Sources remain isolated even when they use the same model ID. Direct requests, routed attempts and inherited child-model requests use these settings, and attempt records retain the effective requested effort. Saving/resetting settings affects subsequent provider resolutions, not already-running requests.
- The composer follows the selected source/model rather than the previous session model. New conversations show the model window even before any usage is reported. Idle sessions recalculate the displayed window/budget after a save or selection change; running/awaiting-approval sessions keep the captured request budget. Historical usage events and cumulative billing totals are never rewritten.
- The reasoning picker uses the effective model override and the catalog's supported levels that the host can serialize. It always retains the current configured effort (including `default`, `none` and `minimal`), even if capability metadata omits it; it never displays the first supported level in place of the configured value. Unknown capability retains the existing choices; metadata alone or focusing/blurring the slider never changes the saved effort. Retaining a configured level is not a claim of upstream support. Adjusting the picker saves only the selected source/model's effort (preserving its other metadata), with revision conflict protection. Legacy selections and route groups retain the global effort control.

Explicit inference tests use the selected model (or the source's default model) and honor its effective protocol/effort/output settings. Queue admission and route-member bindings also use the model's effective protocol and endpoint; changing either after enqueue blocks that queued input rather than silently dispatching it elsewhere. With no configured output limit they request 64 tokens, except Anthropic thinking uses the adapter's 8192-token default to avoid an invalid thinking budget. Catalog checks do not run inference and do not imply inference support. Import accepts user-provided Magpie JSON/deep links, returns a sanitized preview and writes only explicitly selected sources atomically. It does not discover third-party configuration files. Named request cancellation does not retry a mutation.

One source can have multiple enabled API keys/accounts and an explicit selection strategy. Cross-model routing requires a selected group. `provider_attempt` and usage views identify the actual source/model/credential/group without bodies or tokens. `smart`/`pace` use real reported quota; missing quota remains unknown and uses declared order. Known incompatible protocol/tool/vision candidates are excluded. Runtime attempts share one budget; 429 rejection may switch an explicit candidate, but timeouts, 5xx, disconnects, partial output and hosted-search uncertainty do not authorize replay.

Opaque Responses/Anthropic/Gemini state additionally binds source, credential and hashed authentication identity. API-key replacement invalidates it; refresh of a short-lived token for the same stable account does not. Older state without this scope is rebuilt from generic text and complete tool results instead of replaying opaque data.

Codex/ChatGPT and Copilot have explicit device login, refresh and quota modules. Vertex accepts only explicitly provided credential JSON and lazily mints tokens; Azure uses v1 resource URLs and `api-key`; the fixed Magpie Bedrock preset uses bearer API keys, not IAM SigV4. Live subscriptions/cloud resources and all authentication modes are **not** established by fixtures.
