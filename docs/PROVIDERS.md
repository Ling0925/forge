# Provider protocols

`apiMode` selects the OpenAI-compatible HTTP protocol explicitly. Omitted or `chat-completions` uses the existing `/chat/completions` adapter, including its existing streaming and narrowly scoped nonstream fallback. `responses` uses **POST `/responses`** with `stream: true`, `store: false`, `input`, and native flat function definitions (`type: "function"`, `name`, `description`, `parameters`, `strict: false`). Select a mode only when your gateway/model supports that protocol. There is no model fallback, mode autodetection, or automatic replay of an uncertain Responses POST.

Responses input maps system/user/assistant text to role/content items, assistant tool calls to `function_call` items, and matching tool messages to `function_call_output` items keyed by `call_id`. The adapter requires every call to have a matching output before sending the next request. It parses incremental `response.output_text.delta` and `response.function_call_arguments.delta`, validates completed output and IDs against deltas, and only accepts `response.completed` with `status: completed`. Failure, incomplete, error, missing terminal, malformed calls/arguments, unexpected output types, or trailing events reject the response. Request timeout/cancellation and byte/text/event caps also apply. Usage is mapped from `input_tokens`, `output_tokens`, `total_tokens`, and **reported** `input_tokens_details.cached_tokens` (including zero); absent cache counts remain absent. HTTP and protocol errors do not echo server bodies, keys or tool arguments.

Reasoning continuation: `include: ["reasoning.encrypted_content"]` requests opaque reasoning output items. Completed, ordered original output (up to 256 output items; the persisted `providerState` is capped at **256 KiB**, with a 250000-byte wire-output validation) is attached to the exact assistant message as versioned `providerState`, persisted with the session and copied on fork. On matching Responses endpoint and model it replays those original items once, followed by generic tool results; on a different endpoint or model it drops opaque foreign reasoning and serializes generic assistant text and completed tool calls with their paired results. Histories with unresolved or unpaired tool calls reject before the request. A single-response compatibility rule handles gateways whose `response.completed` has `status: completed` but `output: []`: only after stream completion, it uses the ordered original `output_item.done` items when every added item has exactly one matching done item at contiguous indices, unique item IDs, consistent identity, completed function arguments and message text matching tracked deltas and done events, and no conflicting response ID in created/in_progress/completed events. It preserves opaque reasoning from the done event unchanged. Missing terminal, incomplete or failed status, unfinished text/arguments, missing or duplicated items, and conflicting names or call IDs reject before exposing tool calls. Nonempty terminal output remains subject to strict full correspondence with done items; this rule does not synthesize items, retry, replay uncertain requests, or imply support for other gateway deviations. After a validated `response.completed`, the SSE transport may optionally carry exactly one standalone `data: [DONE]` marker (with no event name). It is not a substitute for `response.completed`: premature, repeated, or followed-by-data markers reject; streams without the marker remain valid. Chat Completions requests omit providerState. This metadata is internal state, not display text; redacted/non-resumable exports may omit it. The supported output item types are assistant `message` with `output_text`, `function_call`, and opaque `reasoning`. SSE accepts exact `response.created`, `response.in_progress`, `response.content_part.added/done`, `response.output_text.done`, `response.reasoning_summary_part.added/done`, and `response.reasoning_summary_text.delta/done`, as well as the validated delta/item/completion events described above. `response.reasoning_summary_text.delta` is a bounded, display-only preview forwarded to the provider observer's optional `onReasoning`; it never becomes assistant content and is not the opaque continuation. The accumulated preview (capped at 128 KiB) is also returned on the assistant message's optional `reasoning` field for persistence; Chat Completions `reasoning_content` is handled the same way. Stored `reasoning` is never sent back to the provider. Other lifecycle and multimodal events are unsupported. No native Anthropic or Gemini protocol adapter is provided.

Protocol references: https://developers.openai.com/api/docs/guides/function-calling , https://developers.openai.com/api/docs/guides/streaming-responses , and the OpenAI Responses API reference. Local HTTP fixtures verify implemented wire behavior, **not** authorized gateway interoperability; verify against your own gateway before relying on a specific deployment.
