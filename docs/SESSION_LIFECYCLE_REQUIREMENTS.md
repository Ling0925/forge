# Forge 会话创建时机与空会话治理需求

本文是**会话生命周期**的需求文档：解决"CLI 一启动就创建空会话、导致一堆空会话"的问题。
它描述目标行为、现行实现、改动点、存量数据治理与验收标准，**不是**已通过验收的声明。

- 相关契约：[ARCHITECTURE.md](ARCHITECTURE.md)（会话与持久化）、[CLI.md](CLI.md)、[WORKFLOWS.md](WORKFLOWS.md)、[AUTO_TITLE_REQUIREMENTS.md](AUTO_TITLE_REQUIREMENTS.md)（自动命名，与本需求相关）。
- 术语：**空会话**指 `messages` 为空（`length === 0`）、用户从未发送过任何输入的会话。

## 0 问题陈述

用户报告：**CLI 一启动就创建会话**，即使什么都没说，退出后磁盘上就留下一个空会话；反复启动会累积**一堆空会话**。

经代码核对，该问题**确实存在，且只存在于 CLI**（桌面端已是正确行为，见 §2）。

## 1 需求摘要

1. **CLI 不得在启动时创建会话**；应在用户**发出第一条输入**时才创建。
2. 用户"启动后直接退出"**不留下**任何会话。
3. `/new` 保留"**显式**立即新建"语义（用户主动要求时才建）。
4. 需要决定**存量空会话**如何处理（见 §6）。

## 2 现状（经代码核对）

| 入口 | 创建时机 | 是否符合需求 | 位置 |
| --- | --- | --- | --- |
| **CLI `forge chat` 启动** | **进程启动即创建**（`sessionId` 为空时） | ❌ **需改** | `src/cli/interactive.ts:63-67` |
| CLI `--session <id>` | 恢复已有，不新建 | ✅ | `src/cli/interactive.ts:63-64` |
| CLI `/new` | 用户**显式**输入时创建 | ✅（显式意图） | `src/cli/interactive.ts:455-460` |
| CLI `forge run` | 非交互，已有显式 prompt | ✅ | `src/cli/cli.ts:643-651` |
| **桌面新建任务** | 用户**提交表单**时才创建 | ✅ **已正确** | `src/renderer/components/workbench/Composer.tsx:167-173` |
| 桌面启动 | **不创建**；无活动会话时不渲染输入框 | ✅ | `src/renderer/components/workbench/App.tsx:156` |

关键细节：

- `interactive()` 开头就把 `session` 赋值为**新建的会话**（`interactive.ts:63-67`），此后全程以 `session.id` 参与运行、历史、检查点、诊断等（约 20 处引用，见 `interactive.ts` 内 `session.id`）。
- **创建即落盘**：`store.create` 立即 `atomicJson` 写文件（`src/store/sessions.ts:117-152`，落盘在第 151 行）。因此启动后退出会**真实留下**一个空会话文件。
- 桌面端 `openNewSession(true)` **只打开对话框**（`workbench-context.tsx:293-294` 仅 dispatch），不创建会话——这是桌面端不存在此问题的原因。

## 3 目标

1. 会话的创建时机与"用户表达意图"对齐：**有真实输入才建会话**。
2. 不产生"启动即空会话"的副作用。
3. 保留显式的 `/new` 立即新建语义。
4. 空会话可被识别、可被清理。

## 4 非目标

- 不改变**已有会话**的恢复语义（`--session`、`forge resume`）。
- 不改变**桌面端**的创建时机（它已正确）。
- 不改变子代理 / Fork 的创建规则（它们本身有明确输入）。
- 不引入"自动删除用户会话"的激进行为（清理需显式、可控，见 §6）。

## 5 功能需求

### 5.1 延迟创建（R-C 系列）

- **R-C1**：CLI 交互启动时**不得**创建会话；`session` 改为**惰性**：在首次需要真实运行时才 `createSession`。
- **R-C2**：若用户启动后未输入任何真实内容即退出（`/quit`、Ctrl+C、EOF），**不得**留下会话。
- **R-C3**：多次启动/退出**不得**累积空会话。
- **R-C4**：惰性创建后，会话的 `createdAt`、`title`（含自动命名候选）、`model` 语义与现在一致。
- **R-C5**：`/new` 仍是**显式**立即创建（用户主动要求），且应替换当前活动会话。
- **R-C6**：需要在"尚无会话"状态下支持的交互能力必须明确：
  - `/help`、`/mode`、`/permission`、`/approval`、`/model`、`/queue` 等**不依赖会话**的命令应可用（它们当前多基于内存状态）。
  - 依赖会话的命令（`/sessions`、`/fork`、`/compact`、`/checkpoints`、`/export`、`/diagnostics`、`/context`、`/skills`）在无会话时应给出**明确提示**而非崩溃或偷偷创建。
  - 见 §8 Q1。

### 5.2 空会话识别与治理（R-E 系列）

- **R-E1**：必须能**可靠识别**空会话：`messages.length === 0`，且可结合 `events`/`changes` 为空、`status === "idle"` 判定。
- **R-E2**：需提供**显式**清理手段（见 §6）。
- **R-E3**：清理必须是**用户可见、可控**的动作，不得静默批量删除。
- **R-E4**：清理不得破坏授权/审批/检查点的既有安全语义（见 §7）。

## 6 存量空会话治理（需决策）

现状：**没有删除会话的能力**——`SessionStore`（`src/shared/contracts.ts:58-66`）只有 `list`/`get`/`create`/`save`/`acquire`，**无 delete/remove**；`HarnessService`（`contracts.ts:72+`）也只有 `archiveSession`，**无 deleteSession**。

因此需要决策（见 §8 Q2）：

- **方案 A（最小改动）**：不做删除，仅**修复创建时机**（§5.1）。存量空会话由用户手动 `archive` 收起。
  - 优点：无破坏性操作，改动最小。缺点：存量空会话仍在。
- **方案 B（新增归档引导）**：提供 `/sessions` 中"空会话"标记，并支持批量 archive。
  - 优点：可逆（`archive` 可 `--unarchive`）。缺点：仍需用户手动。
- **方案 C（新增删除能力）**：扩展 `SessionStore` 与 `HarnessService` 增加删除，附带"仅空会话可删"约束与确认。
  - 优点：彻底。缺点：**改动面大**（契约、IPC、CLI、桌面、测试），且引入不可逆删除的风险。

需求倾向：**先 A 止血，再评估 B/C**。

## 7 安全与边界约束（强制）

- **R-X1**：**不得**自动删除任何会话，尤其不得自动删除"看起来是空"但可能含未落盘状态的会话。
- **R-X2**：不得因延迟创建而破坏**取消/中断**语义（Ctrl+C 在无会话时应正常退出，不产生副作用）。
- **R-X3**：不得让"无会话"状态导致**审批绕过**或权限提升。
- **R-X4**：不得在延迟创建时丢失用户已输入的第一条内容（创建与首次运行必须原子衔接）。
- **R-X5**：延迟创建必须与**自动命名**（`AUTO_TITLE_REQUIREMENTS.md`）协调：首轮运行后命名时，会话必须已存在。
- **R-X6**：不得改变 `--session`/`resume` 对已有会话的恢复行为。

## 8 待决问题

- **Q1**：无会话状态下，哪些命令应可用？依赖会话的命令应给出什么提示？
- **Q2**：存量空会话治理选 A / B / C？（见 §6）

## 9 验收标准

- **AC-1**：`forge chat` 启动后立即 `/quit`，**不产生**新会话文件。
- **AC-2**：连续启动/退出 N 次，会话列表中**不增加**空会话。
- **AC-3**：用户输入第一条消息后，会话被创建且内容正确（`createdAt`、`title`、`model`、首条 prompt 完整）。
- **AC-4**：`/new` 仍立即创建会话。
- **AC-5**：无会话状态下，不依赖会话的命令可用，依赖会话的命令给出明确提示且不崩溃。
- **AC-6**：中断（Ctrl+C）、EOF 在无会话时正常退出，无副作用。
- **AC-7**：测试覆盖：启动不建会话、首句才建、`/new` 即建、无会话命令路径。
- **AC-8**：`pnpm typecheck` 与 `pnpm test` 通过；文档同步；CLI 改动按仓库约定 `node scripts/build-core.mjs` 后重开 `forge` 生效。

## 10 风险与约束

- **惰性化的改动面**：`interactive.ts` 中约 20 处使用 `session.id`，需全部改为"会话存在性"安全处理，遗漏会造成崩溃或误建。
- **无删除能力**：存量空会话若要清理，需扩展契约（方案 C），涉及 `SessionStore`、`HarnessService`、IPC、CLI、桌面与测试，成本高。
- **与自动命名的耦合**：自动命名依赖"首轮后会话已存在"，延迟创建后必须保证这一前提。
- **测试回归**：现有交互测试可能假定启动即有会话。
- **并发工作**：工作区存在其他任务的在途改动，实现时不得覆盖。
- **本机流程**：按 AGENTS.md，本机 CLI 更新走"改代码 → `node scripts/build-core.mjs` → 重开 `forge`"，不做完整发布/打包。
